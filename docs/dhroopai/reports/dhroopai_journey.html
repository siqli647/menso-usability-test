Where dhroopAI lost Marek

MAJORSteps 10–14
1. The core promise — 'give us your URL' — failed twice on a public site.
“Ugh, it failed AGAIN — 'could not access this website' even though books.toscrape.com is totally public. That's twice now. Crawling's clearly flaky, so I'm switching routes: 'Add Documents' might let me train it without relying on the crawler.”
Marek gave the onboarding exactly what it asked for: a public website URL. The crawl came back 'could not access this website' — no reason, no diagnostics, no hint whether it was robots, timeouts or the URL itself. He retried; it reached 30% and died the same way. Two failures deep, the product had spent his patience on its one-field promise.
Why this costs trust
Train-on-your-site is the product's first and loudest claim. When it fails opaquely on the very first site an evaluator brings, every later feature inherits the doubt.
Actor friction note · Step 14 · verbatim
The core training workflow — crawling a public URL — failed twice with a vague 'could not access this website' error and no actionable detail ('technical details are saved in server logs for support' doesn't help ME fix it). For a marketer without a developer on call, this is exactly the kind of opaque setup failure that kills trust fast.
What to restore
Return actionable failure reasons (blocked by robots, fetch timeout, TLS, non-HTML), retry automatically with backoff, and show per-page progress so a partial crawl isn't reported as a dead one.
Evidence boundary: Two failures observed against books.toscrape.com this session, with one retry reaching 30% first — whether the site blocks the crawler or the crawler broke is not established from the outside; the error experience is.
MAJORStep 17
2. A raw 400 'Empty instances' API error landed in the customer's modal.
“Ugh, a raw 400 'Empty instances' error dumped right in the UI — that's not something I should ever see as a customer. Crawl failed twice, upload failed... last shot: the Paste Text tab, then I'm making my call on this tool.”
When the crawl kept failing he fell back to Add Documents and uploaded a PDF. The modal answered with a raw JSON API error — 400 INVALID_ARGUMENT, 'Empty instances' — engineering internals rendered where a customer was standing.
Why this costs trust
One unhandled error string undoes a screen's worth of polish: it tells a non-technical buyer the seams are load-bearing, right after the crawler already failed them.
Actor friction note · Step 17 · verbatim
The product exposes a raw 400 INVALID_ARGUMENT API error with JSON internals directly in the user-facing modal — no human-readable explanation, no suggested fix. As a marketing manager evaluating this for lead capture, seeing the core 'train the AI' feature fail three different ways (crawl, retry, upload) with cryptic errors kills my confidence that this runs reliably without a developer babysitting it.
What to restore
Catch upload-pipeline errors at the boundary and translate them ('this file couldn't be processed — try a smaller PDF'), keeping raw API payloads out of the UI.
Evidence boundary: Observed once, for one PDF upload in this session; other file types and sizes were not tried.
MINORStep 10

After the first training attempt the chatbot profile still showed 'Syncing' while recent activity reported the site couldn't be accessed. Marek had to decide which of the product's two voices to believe before he could decide what to do.
Why this costs trust
Contradictory status turns a recoverable failure into distrust — the user stops believing the optimistic signal everywhere it appears.
Actor friction note · Step 10 · verbatim
Conflicting status signals on one screen: the profile says 'Syncing' while recent activity says the site couldn't be accessed. As a marketing manager evaluating this for client sites, ambiguous crawl status with zero pages learned undermines my confidence fast — I shouldn't have to guess which message is true.
What to restore
Drive both surfaces from one status source and flip the profile badge to a failed state the moment the crawl errors.
Evidence boundary: Observed on the dashboard after the first failed crawl of this session.
